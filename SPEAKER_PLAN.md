# One canonical way to resolve a speaker's name

**Status: draft for review. Nothing here is built.**

Five producers name speakers today. Each writes its answer into the same
column, so the archive keeps the verdict and throws away the evidence, and no
two of them agree about what a name is worth. This is a plan to store the
evidence instead and resolve it in one place.

---

## 1. What is wrong now, measured

**The table holds a verdict, not evidence.** `speaker_identity` is one row per
`(video_id, local_label)`: one name, one confidence, one source. When two
methods disagree, one wins at write time and the other is gone.
`bin/speaker_id.py`'s own docstring says "Disagreement between the two is
reported rather than silently resolved" — and the reporting is a `print` to
stdout. Nothing can re-negotiate a name without re-running the pipeline, and
nothing can tell a reviewer *why* a name was chosen.

**The producers do not agree what a confidence means.**

| `source` | rows | mean confidence | written by |
|---|---|---|---|
| `NULL` | 3,345 | 0.70 | `speaker_id.py` — self-ID, clerk announcements, handoff voting |
| `llm` | 1,573 | 0.95 | `name_speakers.py` |
| `chair` | 910 | 0.88 | `chair_anchor.py` |

Three scales, none of them comparable, and the largest bucket does not say
which of three different methods produced it. R5.5.6 already forbids showing
these numbers to a reader on the grounds that they are unmeasured.

**A name someone said out loud is scored lowest of all.** Sean Poole
introduces himself at `1OmEmpL-7qY` idx 414 — *"My name is Sean Poole. I'm
managing director of IntelliRoad."* `SELF_ID` catches it and the archive
resolves the utterance to `Sean Poole`. It stores that as **`basis='voice'`,
`confidence=0.5`** — below the chair's 0.88 and the LLM's 0.95, and described
to every reader by `SpeakerChip` as *"matched by voice at this meeting."* The
voiceprint named nobody. The text did.

That mislabelling is systemic: **all 208,495** `basis='voice'` utterances are
presented as voiceprint matches, and three unrelated kinds of evidence are
underneath them — a person stating their own name, the chair recognising
someone in the room, and an LLM inferring from a transcript.

**Two producers write cluster-wide into a per-voice table.**
`chair_anchor.py` and `name_speakers.py` both `UPDATE ... WHERE cluster = %s`,
while `utterance_speaker` deliberately resolves on `(video_id, local_label)`
because — its own words — collapsing them "merges two people at display time."
`bin/voices.py` measures how bad the assumption is: Starkey's name covers 261
voices in 18 coherent groups, Mariano's 223 in 15, Wilhite's 111 in 10.

**A human label is stored twice.** `voices.py` and `web/admin.py` write
`speaker_label` *and* mirror the name into `speaker_identity` at
`confidence=1.0`. `utterance_speaker` then reads `speaker_label` for
`basis='human'` and `speaker_identity` for `basis='voice'`, so the same human
statement exists as both a human fact and a derived one. Clearing a label sets
`name=NULL, confidence=NULL`, destroying whatever the pipeline had derived
rather than recording that a person detached it.

**The affiliation is never captured at all.** `SELF_ID` is
`my name is (Name)`. It takes the person and drops the clause that follows,
which is where the organisation lives. This is the one defect on this page
that has been observed to corrupt a published answer: an `/ask` run wrote
*"IntelliRoad, a non-enforcement warning system [173152]"* against a passage
that says "our system" and never names the company.

## 2. The model

Three layers, and today's design has them tangled into one.

**Evidence.** Append-only. A producer states what it observed and never
overwrites another producer.

**Resolution.** One function, one precedence, one set of vetoes. Takes every
claim covering an utterance and returns a winner and the reason.

**Presentation.** `SpeakerChip` maps *method* to how sure the page looks, in
one place, as it does now. `web/agent.py` mirrors it for the brief.

### 2.1 `speaker_claim`

```sql
CREATE TABLE speaker_claim (
    id         integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    video_id   text    NOT NULL REFERENCES videos(id) ON DELETE CASCADE,
    -- The SPAN this claim covers, which is what lets specificity break a tie
    -- instead of write order. An override covers a range; a label covers a
    -- voice's whole run in one meeting; a cluster claim covers every
    -- utterance that voice speaks.
    start_idx  integer NOT NULL,
    end_idx    integer NOT NULL,
    -- WHAT WAS OBSERVED and WHO WE THINK THAT IS are two different facts and
    -- they get two columns. `name_text` is the string the transcript actually
    -- carried, ASR warts and all; `person_id` is the resolution, and it is
    -- revisable without touching the evidence. NULL person_id on a human
    -- method means "not this person, and I do not know who" — today's
    -- 'detach'.
    name_text  text,
    person_id  integer REFERENCES people(id),
    org_id     integer REFERENCES organizations(id),   -- §2.5. Nothing
                                -- captures an affiliation today.
    method     text    NOT NULL REFERENCES speaker_method(method),
    quote      text,            -- verbatim support, where the method has one
    author     text,            -- a person, for human methods
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Producers append. Nothing updates. A correction is a new claim, which is how
`speaker_override` already behaves and why it is the one part of this that
does not need changing.

### 2.2 The method vocabulary and its precedence

A table rather than a `CASE`, so the ordering is data and the audit can read
it:

| rank | `method` | what it means | has a quote |
|---|---|---|---|
| 1 | `override` | a person, about this span | — |
| 2 | `label` | a person, about this voice | — |
| 3 | `self` | **they said their own name**, and §2.4 supports it | yes |
| 4 | `rollcall` | the clerk read them in the roll | yes |
| 5 | `chair` | the chair recognised them, in the room, at that moment | yes |
| 6 | `llm` | inference over the same text, quote verified | yes |
| 7 | `voice` | voiceprint match at this meeting | no |
| 8 | `cluster` | the name this voice goes by archive-wide | no |
| — | `self_weak` | a self-ID §2.4 cannot support; ranks below `voice` | yes |
| — | `read_aloud` | somebody reading another person's words; covers only the read span (§2.7) | yes |

**`self` is not only "my name is".** The Florida podium convention is a name,
then an address, then "and I have been sworn" — `SELF_ID` matches none of it,
and 581 utterances use that form. Measured consequence: one voice saying
"Shelley Johnson, 6400 Madison Street, and I have been sworn" is currently
named **"What"**. Both forms are `self` at full strength.

Two deliberate reorderings against today's behaviour.

**`self` moves from the bottom to third**, conditionally — see §2.4. A person
stating their own name is the strongest machine-readable evidence in the
corpus and is currently the weakest thing stored. 665 utterances say "my name
is"; 106 of them (16%) resolve to no speaker at all.

**`llm` moves below direct speech.** It is reading the same transcript and
inferring; where the record says a name outright, the record wins. This is not
a judgement about model quality — `name_speakers.py` verifies its quote and
scores 0.95 — it is about which is the primary source.

### 2.3 Resolution

For an utterance, take every claim whose span contains it, drop the vetoed
ones, and pick by `(rank, span specificity, recency)`.

The vetoes are the two that exist today and both stay exactly as they are:

- **the roster gate** — a board member may not be named at a meeting they did
  not sit in (`load_rosters`, `name_supported`, and the `voice_name`
  predicate). 54,000 utterances, 21% of the archive, once carried
  commissioners who were never in the room.
- **`voice_affinity`** — a cluster name is refused to a voice that scores
  below 0.70 against it. 486 of 1,836 inheritable voices fail this.

A veto suppresses a claim; it never promotes the next one past a human.

`name IS NULL` on a winning claim means *detached*: it suppresses everything
below it and resolves to unidentified, which is what `speaker_override`
already does and what `voices.py` currently expresses by deleting data.

### 2.4 What "the transcript supports it" has to mean

`self` outranks `chair` only where the transcript as a whole bears the name
out. The obvious reading of that — *the name appears somewhere else in the
same transcript* — is the wrong test, and the corpus says so.

    self-stated names                                    1,735
      corroborated elsewhere in the same transcript      1,034  (60%)
      never repeated                                       701  (40%)

The 701 are Jack Brummet, Ted Waller, Sabrina Fernandez — members of the
public who walk to the podium, say their name once, speak, and sit down.
Nobody repeats it because nobody needs to. A rule requiring repetition would
demote exactly the people whose names this archive has just decided to record,
and it would do so for the most ordinary reason there is.

**The risk is not the name; it is the attribution.** Nobody misstates their own
name. What can go wrong is that the "my name is X" utterance is assigned to
the wrong diarization label, so the strongest method names the wrong voice.
That is checkable directly, and it holds for far more of the corpus:

    self-ID utterances carrying a diarization label      1,748
      inside a coherent run (>=4 of 13 neighbours)       1,456  (83%)
      isolated (<=2 of 13)                                 143   (8%)

So the condition is:

1. **Attribution** — the self-ID utterance sits inside a coherent run of one
   voice. This is required. An isolated self-ID becomes `self_weak`, which
   ranks below `voice`: still recorded, still visible to a reviewer, never
   allowed to outrank a voiceprint.
2. **Corroboration** — the name is attested elsewhere in the transcript, in
   the county's own agenda text, or on the clerk's speaker queue. Not required
   for `self`, and it is recorded on every claim that has it.

**Corroboration PROMOTES a weak claim, it does not merely annotate it.**
Judged by hand: at `61kWUVickEs` idx 640 the archive names a voice "David
Engel" from the archive-wide cluster majority — its weakest method — and the
line before it is somebody in the room saying "So David, before you get too
far away". The name is right, and the proof is sitting one utterance away. So
a `cluster` or `voice` claim corroborated by an in-room name cue outranks a
bare one of the same method. The rule is worth having because `cluster` is
22,682 utterances and is the method most likely to be wrong; this is how the
ones that are right earn their place.

A `self` claim that is contradicted — the same span carrying a `label` or a
`rollcall` naming somebody else — is contested (§2.5), not silently demoted.

### 2.4a One person's voice, another person's words

Two cases that looked separate are the same shape, and the maintainer named
it: *"seems similar to a clerk reading an email."*

    a staffer reads a resident's letter    the voice is hers, the WORDS are his
    "on behalf of my son Christopher"      the voice is hers, the INTEREST is his

Both are a speaker whose utterance belongs, in part, to somebody who is not
speaking. The claims model already carries this without new machinery, because
a claim has a span: the read passage gets a `read_aloud` claim naming the
author and covering only those utterances, and the reader keeps every claim
either side of it. Judged by hand at `-KgNtnLj7yg` idx 466, where a staffer
reads a letter opening "My name is Corey Ward" — and where a naive `self`
claim would have named her Corey Ward at rank 3, above the voiceprint.

Keep the two distinguishable rather than flattening them. Reading a letter is
**verbatim**: those are the author's own words and a reader may quote them as
his. Speaking on behalf is **advocacy**: the words are the speaker's and only
the interest is borrowed. An archive that confused the two would let somebody
quote Valerie Phillips as though she were her son.

Rendering, decided: **the author, marked as read aloud** — "Corey Ward, read
by staff". Two facts, both true, and a reader learns whose words these are and
that he was never in the room. `SpeakerChip` needs a state for it.

### 2.5 Contested becomes a fact rather than a print statement

Today `contested` means only "a pending human override exists". With claims it
also means **two unvetoed methods assert different names for the same span** —
which the pipeline already computes and discards. That number is the natural
sort order for the review queue in `web/admin.py`, and it is the measurement
that would tell us whether any of this is working.

### 2.6 Organisations are entities, exactly as people are

`people` is four columns — `id`, `surname`, `full_name`, `UNIQUE (surname)` —
and everything else about a person is derived: `display_name()` folds the key
to what is printed, `tools.canonical_speaker` folds it back, and the roster
decides where the name may be used. Organisations get the same treatment and
for the same reason: a firm appears under several spellings and must resolve to
one thing.

```sql
CREATE TABLE IF NOT EXISTS organizations (
    id    integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    -- The county's own spelling, from its own documents. NOT the transcript's.
    name  text NOT NULL,
    kind  text,          -- 'applicant' | 'vendor' | 'firm' | 'agency' | NULL
    UNIQUE (name)
);

-- What the room actually said. ASR renders a company name several ways and
-- every one of them has to reach the same row: this archive already contains
-- "IntelliRoad" spoken once and written once, and a person introduced as
-- "Barbara Will Hyde" against a roster saying Barbara Wilhite.
CREATE TABLE IF NOT EXISTS organization_alias (
    alias  text PRIMARY KEY,
    org_id integer NOT NULL REFERENCES organizations(id) ON DELETE CASCADE
);
```

**An affiliation is read by a model, not by a regex, and verified against the
record.** The clause after a name has no stable form. From one sample of 22:
"I'm your Director of Utilities for Pasco County", "I work for a group called
John Burns Real Estate Consulting", "Senior Purchasing Agent for the
Purchasing Department", "I also serve on the board of the Gulf Harbor Civic
Association". Four shapes, and separating a vendor from a county department
from a civic association is semantic. A pattern would be guessing.

`name_speakers.py` already proves the safe division of labour and it applies
here unchanged: **the model proposes, code verifies.** The verification is
stronger for organisations than it is for names, because the county publishes
the org itself — so the task is MATCHING a heard affiliation to an
`organizations` row seeded from `agenda_items`, not inventing one. A proposal
that matches nothing published is a candidate for review, never a write.

It is also a small job. Most people who introduce themselves have no
affiliation to find:

    self-ID utterances                                   1,748
      residents giving a home address, no affiliation    1,182  (68%)
      carrying any professional marker                     311  (18%)

So the pass runs over ~311 candidates rather than 1,748, which is one batch.

`kind` matters more than it looks, and the corpus needs more of them than a
vendor list. What people actually say they represent, from three consecutive
samples: *"I am the president of ou[r]…"*, *"on behalf of the Panther Run
subdivision"*, *"on behalf of my son Christopher Phillips"*. A civic
association, a subdivision, a family member. IntelliRoad — the vendor case
that started all this — is the minority.

So: **subdivisions and homeowners' associations are organisations with their
own kind**, decided, because "who spoke for Panther Run" is a question this
archive should answer and they recur across meetings. `kind` spans
`applicant | vendor | firm | agency | association | subdivision`. County
departments — "Purchasing Department", "Pasco County Utilities" — are the
county itself and get their own kind or stay out; folding them in with vendors
would pollute the one query this table exists to answer.

And a person is not an organisation: "on behalf of my son" is §2.4a's
speaking-for relation, whose target is sometimes an org and sometimes a
person.

**Seeded from the published record, not from speech.** `people` is seeded from
the county's roster; organisations are seeded from `agenda_items` — the
applicant on a rezoning, the firm on a contract, the vendor on an award are all
named in `title`, `recommendation` and `disposition`, in the county's own
spelling. A name heard at the podium is then matched to that, which is the
same direction of trust the rest of the archive uses: the record names things,
the transcript says what was said about them.

This is worth more than the speaker fix that motivates it. "Which firm appeared
for which application", "every meeting this vendor was awarded something", and
an entity facet on `/search` all become queries rather than full-text guesses —
and §5 of `PRIOR_ART.md` is already pointing at entities for the same reason.

### 2.7 `person_id` is the key. A name is an attribute.

Decided: everybody named becomes a person, and — the maintainer's objection,
which is correct — **nothing joins on a surname.**

Today `people` is `UNIQUE (surname)` and the speaker layer reaches it by
`JOIN people p ON lower(p.surname) = lower(si.name)`. That is a natural key
made of data that changes: ASR renders it three ways, a correction rewrites
it, and the schema's own comment concedes that "the day two boards seat the
same surname that uniqueness is already the defect". A string join also drags
case-folding and whitespace into what should be a foreign key.

The good news is that the rot is contained. `board_terms` and
`meeting_roster` already key on `person_id`; the roster layer is properly
normalised. It is only the SPEAKER tables — `speaker_identity`,
`speaker_label`, `speaker_override`, `voice_name` — that store a name string
and join back on it, and those are exactly the tables this plan replaces. So
this is not separate work; it is work this plan should not have skipped.

```sql
people (
    id           integer PRIMARY KEY,
    kind         text NOT NULL,   -- 'board' | 'staff' | 'public'
    -- What a reader sees. Chosen ONCE, correctable in one place, and no
    -- longer computed from a surname by a SQL function.
    display_name text NOT NULL,
    -- An attribute of board members, because the roster publishes it. NOT a
    -- key, NOT unique, and nothing joins on it.
    surname      text
);

-- Every rendering ever heard, pointing at one person. This is where "Jack
-- Brummet" and "Jack Brummett" both live, and "Barbara Will Hyde" beside
-- "Barbara Wilhite".
person_alias (
    alias     text PRIMARY KEY,
    person_id integer NOT NULL REFERENCES people(id) ON DELETE CASCADE
);
```

**This dissolves §1a rather than answering it.** The ASR-variant question —
which of two spellings wins — stops being a fight to be settled per utterance
and becomes one field on one row. Both renderings are aliases of one person;
`display_name` is chosen once and corrected once. "Most frequent rendering
wins" survives only as the rule for SEEDING that field, not as a resolution
rule, and a human can overrule it with a single update instead of a campaign.

**It also retires `display_name(nm text)`.** That function exists purely to
paper over the surname key — given a string, find the person, return a better
string. With `person_id` on the claim, the resolver returns a person and the
display name is a column on it.

What has to move, and all of it is board-scoped: the roster join in
`web/admin.py`, `speaker_id.load_rosters()` and its term fallback,
`chair_anchor`'s cluster-to-surname map, `voice_name`'s roster predicate,
`audit.py`'s one-body-per-surname assertion, and `tools.canonical_speaker`
with the `speaker` search facet behind it.

**One name string is kept on purpose**, and it is not a key.
`passages.speaker` and the rendered `text` carry the name INTO the search
index, because "what did Starkey say about X" needs it in the BM25 postings
and in the embedding — `index_passages` says so and rebuilds both when a name
changes. A denormalised copy in an index with a defined refresh path is a
different animal from a join key, and it stays.

## 3. Materialise it, and retire a workaround

`utterance_speaker` resolves four levels per row at read time and costs
**620ms per 600 passages against 2ms without it** — one of those levels
recomputes the archive-wide cluster majority per row. A more general resolver
over a claims table is strictly worse if it stays a view.

Resolution changes only when a claim is added, so the resolved name belongs in
a **table refreshed on write**, not a view computed per read. That fixes the
latency and the correctness together, and it retires `passage_speaker` and
`tools.speaker_sure`, which exist only to work around the current cost.

`utterance_speaker` keeps its current columns — `name`, `display_name`,
`basis`, `human`, `confidence`, `contested` — so that the twelve files reading
only the view need no change. `basis` becomes the method, which is strictly
more informative than the four values it carries now.

## 4. Migration

Twelve files read only the view and do not move. Ten touch
`speaker_identity`; **five write it**, and those five are the work:

| writer | today | becomes |
|---|---|---|
| `bin/speaker_id.py` | writes rows, `source=NULL` | appends `self` / `rollcall` / `chair` / `voice` claims, each with its quote |
| `bin/chair_anchor.py` | `UPDATE … WHERE cluster` | appends `chair` claims per voice |
| `bin/name_speakers.py` | `UPDATE … WHERE cluster` | appends `llm` claims per voice, with `evidence_quote` |
| `bin/voices.py` | writes `speaker_label` + mirrors | appends `label` claims only |
| `web/admin.py` | writes `speaker_label` + mirrors | appends `label` claims only |

Order:

1. `speaker_claim` + `speaker_method`, and the resolver, alongside the
   existing tables. Nothing reads it yet.
2. Backfill from `speaker_label`, `speaker_override` and `speaker_identity`.
   The 3,345 `source IS NULL` rows cannot be classified after the fact — they
   are re-derived by re-running `speaker_id`, which `PIPELINE_PLAN.md` clocks
   at **2m17s for all 432 recordings**. Guessing is not worth 137 seconds.
3. Re-implement `utterance_speaker` over the resolver, same columns. Diff the
   old and new resolution over all 234,000 named utterances and require the
   differences to be explainable — every one should be a `self` or `chair`
   claim correctly outranking a `voice` claim.
4. Convert the five writers.
5. Materialise, and delete `passage_speaker` / `speaker_sure`.
6. Add the affiliation: extend self-ID capture to the clause after the name,
   and carry `org` onto the passage line in `web/agent.py`.

Step 3 is the gate. If the diff is not explainable, stop.

## 4a. Proving it before committing to it

Nothing above is switched on until it has been shown to be better. The whole
build runs in **shadow**: `speaker_claim`, the resolver, and a SECOND
materialised table alongside the live one. No reader changes, no writer
changes, and the old path keeps serving every page. Shadow is deleted by a
`DROP`, which is what makes this reversible.

Four measurements, weakest evidence to strongest.

**1. The diff, categorised.** Resolve all 234,000 named utterances both ways
and bucket every difference by `(old basis -> new method)`. This is a
description, not a verdict: it says what changed and how much, and the
expected shape is one dominant bucket, `voice -> self`, plus a smaller
`voice -> chair`. A large bucket nobody predicted is a reason to stop.

**2. Held-out human labels.** Hide every human statement from the resolver,
resolve, and count how often each path lands on the name the person chose.
This is the only direct accuracy measurement available and it is
**underpowered**, which has to be said plainly:

    speaker_label rows                                      72
      across recordings                                     63
    applied speaker_override rows                            0

Seventy-two independent judgements can detect a large difference and nothing
subtle. Zero applied overrides also means the `override` method — rank 1, the
top of the precedence table — has never run in production and cannot be tested
this way at all.

**3. The agent eval, end to end.** `bin/eval_agent.py --agent` against shadow
and against live. Independent of everything above, because it measures the
thing a reader actually receives, and it has a baseline: 3 failures then 2,
over four questions, in the two runs recorded in gotcha 98. Also underpowered
at n=4, and its failures are mostly not speaker-shaped.

**4. Spot-check the disagreements.** Sample the buckets from (1) by hand.
Fifty is enough to find a systematic error and is an hour's work.

**And the honest conclusion: the archive cannot currently tell you whether
this is "obviously better" to any precision.** It has 72 human judgements. If
that answer is wanted rather than a plausible argument, the cheap route is to
make more ground truth first — the review screen in `web/admin.py` already
exists and already sorts a queue, and 200 labelled utterances stratified
across methods is an afternoon. That is worth doing BEFORE the migration
rather than after, because it is the only thing that can grade it.

## 5. What `bin/audit.py` must assert once this exists

- No resolved name for a board member at a meeting whose roster excludes them.
  (Holds today; must keep holding.)
- Every `self`, `rollcall`, `chair` and `llm` claim's `quote` appears verbatim
  in the utterance range it covers. `name_speakers.py` verifies this at write
  time for its own claims; nothing re-checks it afterwards, and a redaction can
  change the text underneath.
- No claim spans utterances from more than one `video_id`.
- The materialised table agrees with the resolver recomputed from scratch —
  this is the check that a stale materialisation cannot hide.
- Contested count, reported rather than asserted. It is a workload measure,
  not a failure.

## 6. What this fixes, and what it does not

**Fixes.** Three kinds of evidence stop being called a voiceprint match. A
self-stated name outranks a guess instead of scoring half of one. Human labels
stop being stored twice. Disagreement becomes queryable instead of printed.
The read cost of a resolved name goes to zero. And `org` capture removes the
gap that produced the IntelliRoad error.

**Does not fix.** Of the five `/ask` failures catalogued in `STATE.md` gotcha
98, this reaches **two** — both the vendor-attribution shape, and both through
`org` rather than through the resolver. It does nothing for a writer
over-reaching on a summary, nothing for arithmetic no passage carries, and
nothing for the judge's own errors. It should be justified as a correctness
fix to the archive, not as an answer-quality fix, and measured on the eval
afterwards rather than assumed.

**Does not address.** 1,717 unnamed voices sit outside `name_speakers.py`'s
`lines >= 60 AND mtgs >= 2` gate, 1,153 of them single-meeting, and **196 of
them state their own name out loud**. That is a separate and much cheaper
change — point the existing pass at a population it was never aimed at — and
it does not need any of this.

## 7. Decided, and still open

**Decided.**

- `self` outranks `chair`, conditional on the transcript bearing the name out.
  §2.4 defines that as an ATTRIBUTION test rather than a repetition test,
  because 40% of self-stated names are never repeated and those 40% are the
  members of the public this archive has just decided to record.
- Organisations are first-class entities, mirroring `people` (§2.6).
- Public-commenter names are recorded, with accuracy as the constraint rather
  than identifiability. Nothing here redacts a name; `bin/redact.py` continues
  to own home addresses, which is a separate axis.
- The resolved name is materialised (§3).
- Nothing is switched on until it is shown to be better, and the whole build
  runs in shadow until then (§4a).
- Affiliations are read by a model and verified against the published record,
  not parsed (§2.6).
- `self` covers the "<Name>, <address>, and I have been sworn" convention as
  well as "my name is" — 581 utterances the regex ignores today (§2.2).
- Corroboration promotes a weak claim rather than merely annotating it (§2.4).
- Read-aloud and speaking-for are one mechanism, rendered as the author marked
  as read aloud, and kept distinguishable: verbatim words versus borrowed
  interest (§2.4a).
- Subdivisions and associations are organisations with their own kind (§2.6).
- One `people` table for everyone, keyed on `person_id`. Nothing joins on a
  surname; a name is an attribute and `display_name()` retires (§2.7).

**Open.**

1. **Where does the `self_weak` line sit?** Still open, and now known to be
   unanswerable from text: put to the maintainer with full context, the verdict
   was *"need to listen to tell."* Calibrating it needs audio, so the labelling

1a. **~~How is an ASR-variant name normalised?~~** Closed by §2.7. Both
   spellings become aliases of one `person_id` and the display name is one
   field, so majority-vote survives only as a seeding heuristic. Worth keeping
   the measurement that made it look urgent: of 1,449 self-IDs with a resolved
   name, 1,312 already agree and only 137 differ — and most of those 137 were
   never a precedence problem at all.
2. **Make ground truth before migrating, or accept a weak grade?** §4a can
   describe what changed and argue it is right; with 72 human labels it cannot
   prove it. 200 stratified labels through the existing review screen is an
   afternoon and is the only thing that turns the argument into a measurement.
   This is the decision that governs the schedule.
3. **Who seeds `organizations`?** §2.6 says the agenda text, which needs a
   parser, and `parse_agenda` is a parser that already reads those fields.
   Whether that is an extraction pass or a curated list to start with is a
   scope decision, not a design one.
4. **`org` on a claim is per-appearance, deliberately.** A person's affiliation
   changes between meetings — an engineer moves firms, an attorney appears for
   a different applicant — so the claim carries `org_id` and the organisation
   row carries only the identity. If a durable "X works for Y" is ever wanted,
   it is a separate relation and should be argued separately.
